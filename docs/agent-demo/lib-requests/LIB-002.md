# LIB-002: RubyLLMの自動tool loopでstream key再利用が衝突する

状態: fixed  
担当: `/root/lib_fixes`  
アプリをブロックするか: yes（RubyLLMで異なるtoolを複数stepにわたり呼ぶ経路）

## SDK/model/呼び出し条件

- `ruby_llm` 1.16.0
- `Chat#ask` のstream blockへchunkを渡し、`after_message` callbackからtool-result `RubyLLM::Message` を同じEnumeratorへ渡す
- tool call後にRubyLLMが `complete` を再帰し、次のprovider completionでもtool stream key `0` を使う

## 最小再現・証拠

tool call `call-stock` をstream key `0` で受け、tool result後の次completionで別tool `call-sales` が同じkey `0` を使うevent列をadapterへ渡す。修正前はadapter内の `@tool_ids_by_stream_key[0]` が `call-stock` のまま残るため、`already identifies` errorになる。

installed RubyLLM 1.16.0の `lib/ruby_llm/chat.rb` では、assistant responseを追加して `after_message` を呼び、toolを実行してtool-result Messageを追加後に `complete` を再帰する。provider側のstream accumulatorはcompletionごとに作られるためstream keyは再利用される。

## 期待と実際

- 期待: tool result後の次provider completionを新しいUI stepとして扱い、stream keyをstep内だけで対応づける。全completionのusageをmessage metadataへ集計する。
- 実際（修正前）: UI上は全loopが1 stepで、前completionのkey bindingが別toolを拒否し、usageは最後のusage-bearing chunkだけだった。

## 修正

- 1件以上のtool-result Message後、最初の次chunkで `finish-step` / `start-step` を出す。
- step切替時にtool stream key、latest tool、text/reasoning part IDをresetする。provider固有call IDのtool状態はoutput対応のため保持する。
- completionごとの最終usage snapshotを保持し、数値fieldをtool loop全体で合算する。
- tool実行は従来どおりRubyLLM/app側で、adapterはcallback eventの変換だけを担う。

変更: `lib/ai_stream/adapters/ruby_llm.rb`, `sig/ai_stream.rbs`, README（日英）  
回帰test: `test/ai_stream/adapters/test_ruby_llm.rb` の異なる2tool、3step、key `0` 再利用、usage合算

# LIB-001: OpenAI Responses adapterが1回目でUI messageを終端する

状態: fixed  
担当: `/root/lib_fixes`  
アプリをブロックするか: yes（OpenAIの複数step tool loop）

## SDK/model/呼び出し条件

- `openai` 0.85.0のResponses streaming API
- 1ユーザーrequest内で、function call responseへtool結果を返して次のResponses callを行う
- 次のcallは `previous_response_id` と `function_call_output` inputを使う

## 最小再現・証拠

既定のOpenAI adapterを同じ `UIMessage::V1::Stream` へ2回順番に流すと、1回目が `finish` と `[DONE]` を出す。2回目のeventは `Stream::FinishedError` になる。また、stepだけをadapterに所有させると `response.completed` で `finish-step` が出るため、その後にアプリがtool outputを同じstepへ追加できない。

OpenAI公式API referenceでは、`previous_response_id` で会話状態をつなぎ、`function_call_output`を次のinput itemとして渡せる。一方、前responseのinstructionsは自動で引き継がれないため再送が必要である。

- https://developers.openai.com/api/reference/resources/responses/methods/create
- https://developers.openai.com/api/docs/guides/function-calling

## 期待と実際

- 期待: アプリがtool実行とmessage/step lifecycleを所有しながら、各Responses streamのprovider eventだけをadapterで変換できる。
- 実際（修正前）: adapterが常にmessageとstepの両方を終端し、tool outputを挿入して次provider callへ進めない。

## 修正

- `lifecycle: :content` を追加した。このモードはprovider contentと完了時の `message-metadata` のみを出す。
- 既定の `:message` は互換維持し、`:step` はmessage境界だけを省く。
- OpenAI adapterは列挙後に `response` と `finish_reason` を公開する。
- tool実行、tool結果のcache、次Responses requestの構築はアプリ側に残す。
